# AI Workflow Rules

How the agent works on this project. These are rules, not suggestions. Read them before opening a spec or starting a unit. They mirror the AI Builder's Playbook in `docs/ai-builders-playbook.md` and tighten it for outbound-spotter's stack.

## Approach

- **Spec-driven.** No code lands without a `context/specs/NN-*.md` file. The spec is the source of truth; if the spec is wrong, fix the spec first, then implement.
- **Incremental.** One unit at a time, one feature boundary per unit. The verification checklist in the spec is non-negotiable.
- **Context-first.** Every session starts by reading `CLAUDE.md`, which routes you to the six context files. Don't skip — and don't replace the files with your own assumptions.
- **Plan before code on anything non-trivial.** Use `/plan` mode (built-in) when scope, sequencing, or architecture is unclear. Implement only after the plan is approved.
- **Documentation precedes implementation.** When something is ambiguous, write the resolution into the relevant context file (or open question in `progress-tracker.md`) *before* writing the code.

## Scoping rules

- **One unit per branch.** `feat/NN-feature-slug` off `develop`. Don't reach across units within the same branch.
- **One system boundary per unit.** A unit either changes UI, or backend, or shared types — not all three. If a feature genuinely crosses boundaries, split it into ordered units (backend first, frontend second).
- **No speculative changes.** Don't refactor unrelated code "while you're there." Open a separate `refactor:` PR if the cleanup is worth it.
- **Trust internal code.** Don't add defensive validation between functions inside the same module. Validate at the boundary (HTTP, file, env), then trust the rest of the call graph.

## When to split a unit

Split if the unit currently combines:

- UI changes **and** database changes (split into "BE: model + endpoint" → "FE: form + render").
- Multiple unrelated API routes (one route per spec when each delivers a distinct user value).
- Behavior not clearly defined in the context files (resolve the open question first, *then* split the implementation).
- A backend module **and** a new third-party integration setup (split the dependency wiring out of the feature spec).
- More than one verification path that someone would manually click through.

If a change cannot be verified end-to-end in a single focused session, the scope is too broad — split.

## Handling missing requirements

1. **Check the context files first.** The answer often already lives in `project-overview.md`, `architecture.md`, `code-standards.md`, or `ui-context.md`.
2. **Then check `docs/`.** The FMCSA HOS guide (`docs/interstate-truck-driver-guide.md`) is the regulation source of truth. The assessment brief (`docs/assesment.md`) is the product brief. The theme (`docs/theme.md`) is the visual source of truth.
3. **If still ambiguous:** add a bullet under `## Open Questions` in `progress-tracker.md` with the specific question and the candidate answers. Do not invent product behavior. Do not pick a regulation interpretation without citing §395.
4. **Verify against live documentation, not memory.** Model knowledge of fast-moving libraries drifts. Use WebFetch / WebSearch on official docs (vite.dev, react.dev, ui.shadcn.com, docs.djangoproject.com, clerk.com/docs, openrouteservice.org, leafletjs.com, turborepo.com) before encoding a pattern that will be reused. Cite the version you verified against in your output.

## Protected files

Do **not** modify these without an explicit spec instruction:

- `apps/web-app/src/components/ui/**`, `apps/web-auth/src/components/ui/**` — shadcn-generated. Update via `pnpx shadcn@latest add <component>`.
- `apps/web-api/openapi.yaml` — generated by `drf-spectacular`. Regenerate via the management command.
- `.agents/skills/**` and `~/.claude/plugins/**` — installed by the skills + plugin tooling.
- `pnpm-lock.yaml`, `uv.lock`, `requirements.lock`, equivalents — let the package manager produce these.
- Django migration files after they've been applied to *any* environment (CI, staging, prod). Add a new migration to fix; never re-edit.
- `docs/**` — read-only reference material.

## Sub-agents (from the `wshobson/agents` marketplace)

We use only enterprise-validated agents. The marketplace `claude-code-workflows` is declared in `.claude/settings.json#extraKnownMarketplaces`; the enabled plugins are listed in the same file.

| Plugin                      | Agents to invoke                                      | When to use                                                                                                            |
| --------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `comprehensive-review`      | `code-reviewer`, `architect-review`, `security-auditor` | Before opening a PR; before merging into `develop`; after any change touching auth, JWT verification, or ORS proxying. |
| `unit-testing`              | `test-automator`                                      | When a new module needs Pytest or Vitest tests, or to fix a failing test suite.                                        |
| `javascript-typescript`     | `typescript-pro`, `javascript-pro`                    | Any change in `apps/web-app` / `apps/web-auth`. Picks up React 19 patterns and the `react-doctor` skill rules.         |
| `python-development`        | `python-pro`, `django-pro`                            | Any change in `apps/web-api`. Picks up the `django-expert` skill rules.                                                |
| `accessibility-compliance`  | `ui-visual-validator`, `wcag-audit-patterns` skill    | After any UI change. Mandatory after the trip form, log SVG, and auth screen units.                                    |
| `application-performance`   | `performance-optimizer`                               | After unit completion if the unit added a route, list, or data fetch. Required before the deployment unit.             |

- **Do not author custom sub-agents.** If a gap exists, surface it as an Open Question; we install validated agents only.
- **Invoke explicitly when delegation matters.** `Use the code-reviewer agent to review this branch.` — that wording delegates the work to the right agent instead of leaving it to auto-routing.
- **Sub-agents return summaries; do the synthesis yourself.** Don't write "based on its findings…" — read the summary and own the next step.

## Skills

Skills live under `.agents/skills/` and are visible via the `.claude/skills` symlink. Each fires on its own triggers; this table is just so future sessions know what's loaded:

| Skill                       | Auto-triggers on                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `shadcn`                    | `components.json` present; "add a component", "shadcn", or styling tasks.                 |
| `tailwind-theme-builder`    | Tailwind v4 setup, `@theme inline` issues, dark mode toggle, v3 → v4 migration mentions.  |
| `react-vite-best-practices` | Editing Vite config, bundle, code splitting, HMR, or React perf in `apps/web-app`.        |
| `django-expert`             | Editing `settings.py`, `models.py`, DRF serializers, viewsets, ORM, auth in `apps/web-api`. |
| `turborepo`                 | Editing `turbo.json`, task pipelines, `--filter` / `--affected`, remote caching.          |
| `react-doctor`              | Writing or reviewing React code — applies its 60+ rules (useEffect misuse, derived state, perf, a11y, security). |

If a skill doesn't auto-trigger, invoke it explicitly with `/<skill-name>` rather than re-deriving the rules.

## Keeping documentation in sync

Update the relevant context file **before** continuing whenever implementation changes:

- A folder owner / system boundary — update `architecture.md#System Boundaries`.
- A storage decision (new table, blob, cache) — update `architecture.md#Storage Model`.
- An invariant (a new rule the code must respect) — update `architecture.md#Invariants`.
- A code convention (lint rule, naming, layout) — update `code-standards.md`.
- A token, font, spacing, or motion choice — update `ui-context.md`.
- A scope decision (in/out of v1) — update `project-overview.md#Scope`.

The progress tracker is a *running journal*, not a spec store — it captures phase, completed units, in-progress unit, open questions, and decisions. Update it after every meaningful change.

## Verification before moving to the next unit

The unit is not done until *all* of the following hold:

1. The verification checklist in the spec is fully ticked.
2. No invariant from `architecture.md` was violated.
3. `progress-tracker.md` reflects the completed work and is the *last* file you commit.
4. CI passes locally: `pnpm turbo run lint typecheck test build --filter=<affected>`. For `web-api`: `uv run pytest`, `uv run mypy`, `uv run ruff check`.
5. `code-reviewer` (from `comprehensive-review`) has reviewed the diff and any criticals are resolved.
6. For UI units: `accessibility-tester` has reviewed.
7. For HOS-touching units: the golden tests pass *and* the change references the specific FMCSA section it interprets.
8. The branch is rebased on `develop`; the PR opens against `develop`, not `main`.

If any of these fail, the unit is not complete. Either fix or split.

## Anti-patterns (don't)

- **Don't fabricate a pattern** because "you've seen it before." Verify against the actual installed version. Library APIs change.
- **Don't chase test green by mocking the regulation.** Pytest scenarios for the HOS planner test the regulation, not the wiring. If a test is hard to write because the regulation is ambiguous, that's the test telling you to clarify the regulation interpretation first.
- **Don't bypass the marketplace.** No new custom sub-agents under `.claude/agents/`. If a workflow is missing, file an Open Question.
- **Don't push to `main` directly.** Ever. `develop` is for integration; `main` is for releases via PR from a release branch.
- **Don't add dependencies just-in-case.** Each package install needs a callsite in the spec it lands with. Untouched dependencies are noise.

## Session bootstrapping

A new Claude Code session in this repo should always:

1. Read `CLAUDE.md` (auto-loaded).
2. Read the six context files in order.
3. Read `progress-tracker.md` to see where the project stands.
4. Confirm the active marketplace + plugins are loaded — `claude plugin list --scope project` should show all six plugins enabled.
5. Confirm the skills are visible — `ls .claude/skills/` should show six skill directories.

If any of these fail, fix the environment before writing code.
